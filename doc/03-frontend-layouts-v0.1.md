## 라우트

라우트는 5개다. 그 외에 404가 있다.

| 라우트          | 경로                                        | 레이아웃        |
| --------------- | ------------------------------------------- | --------------- |
| **Login**       | `/login`                                    | `AuthLayout`    |
| **Signup**      | `/signup`                                   | `AuthLayout`    |
| **Dashboard**   | `/`                                         | `ProjectLayout` |
| **ProjectForm** | `/projects/new`<br>`/projects/:id/settings` | `ProjectLayout` |
| **SpecDetail**  | `/projects/:id`                             | `SpecLayout`    |

멘션 알림 딥링크 (백엔드 확정):
`/projects/:projectId/endpoints/:endpointId?comment=:commentId`
→ 해당 댓글로 스크롤 + 하이라이트. 초대 알림은 프로젝트로만 이동.

## 라우트별 레이아웃

| 라우트          | 헤더 좌                                        | 헤더 우                   | 본문                            | 푸터     |
| --------------- | ---------------------------------------------- | ------------------------- | ------------------------------- | -------- |
| **Login**       | — (헤더 없음)                                  | —                         | 중앙 정렬 · `max-w` 모바일 너비 | x축 중앙 |
| **Signup**      | — (헤더 없음)                                  | —                         | 중앙 정렬 · `max-w` 모바일 너비 | x축 중앙 |
| **Dashboard**   | `Dashboard`                                    | 아바타                    | 일반 흐름 · 페이지 스크롤       | x축 왼쪽 |
| **ProjectForm** | `←` + 프로젝트명                               | 아바타                    | 일반 흐름 · 페이지 스크롤       | x축 왼쪽 |
| **SpecDetail**  | `←` + 프로젝트명 + 프로젝트 설정 버튼(Owner만) | Bearer 토큰 입력 + 아바타 | 3컬럼 · 컬럼별 독립 스크롤      | x축 왼쪽 |

> ProjectForm 헤더 좌측: 생성 모드는 `새 프로젝트`, 편집 모드는 프로젝트명.
> 프로젝트명은 길면 `truncate`.

### `⚙`(프로젝트 설정)이 헤더 좌측에 있는 이유

좌측은 "이 프로젝트가 무엇인가"를 말하는 영역(`←` + 이름)이다.
`⚙`를 그 옆에 두면 **이 프로젝트에 대한 액션**으로 읽힌다.
우측(Bearer · 아바타)은 "도구 · 계정"으로 성격이 통일된다.
Owner에게만 보인다(Member는 설정을 고칠 수 없음).

### Bearer 토큰 입력이 헤더에 상주하는 이유

Try it으로 여러 엔드포인트를 연속 테스트할 때,
토큰을 고치려고 매번 스크롤을 올리거나 팝오버를 여닫는 것은 실사용에서 큰 마찰이다.
그래서 **어느 폭에서도 접히거나 숨지 않는다.** 팝오버·아코디언으로 대체하지 않는다.

## 레이아웃 3종

| 레이아웃        | 담당 라우트             | 하는 일                                                                |
| --------------- | ----------------------- | ---------------------------------------------------------------------- |
| `AuthLayout`    | Login · Signup          | 헤더 없음. 본문을 화면 중앙에 두고 모바일 너비로 제한. 푸터 중앙 정렬. |
| `ProjectLayout` | Dashboard · ProjectForm | `<Outlet>` + 푸터(왼쪽). **헤더는 그리지 않는다.**                     |
| `SpecLayout`    | SpecDetail              | `h-dvh` flex 세로 스택. 3컬럼이 남는 높이를 차지한다.                  |

### 헤더를 레이아웃이 아니라 페이지가 그리는 이유

Dashboard와 ProjectForm은 헤더 좌측 내용이 다르다(고정 텍스트 vs `←`+프로젝트명).
레이아웃이 헤더를 그리면 자식(페이지)이 부모(레이아웃)에게 내용을 올려보내야 해서
Context나 `useMatches` 같은 우회가 필요해진다. 페이지가 5개뿐인 규모에서는 과하다.

대신 **각 페이지가 `<Header left={…} right={…} />`를 직접 렌더**한다.
헤더 뼈대는 `Header` 한 곳에만 있으므로 중복이 아니고,
"이 페이지의 헤더가 무엇인지"가 그 페이지 코드에 그대로 보인다.

### SpecDetail을 ProjectLayout에서 분리하는 이유

헤더 때문이 아니라 **본문 구조** 때문이다.
Dashboard·ProjectForm은 콘텐츠가 흐르고 페이지 전체가 스크롤되지만,
SpecDetail은 화면 높이에 고정되고 3컬럼이 각자 스크롤한다.
같은 레이아웃에 넣으면 높이 계산과 스크롤 소유권이 조건 분기로 얽힌다.
헤더(`Header`)와 푸터(`Footer`)는 그대로 공유하므로 중복은 없다.

## 헤더

### 뼈대

`Header`는 `left` · `right` · `wide` 세 슬롯을 props로 받는다.
`sticky top-0 z-50`이며, **스크롤 컨테이너 밖**에 두어야 한다
(`sticky`는 부모에 `overflow: hidden/auto`가 있으면 동작하지 않는다).

### 반응형

헤더는 3컬럼과 독립된 구조이므로 반응형을 처음부터 확정해 둔다.
브레이크포인트는 **`md`(768px)** 하나만 쓴다.

```
데스크탑 (≥ md)
┌──────────────────────────────────────────────┐
│ ←  결제 API  ⚙        [Bearer 토큰__]  아바타 │   1행
└──────────────────────────────────────────────┘

모바일 (< md)
┌────────────────────────────┐
│ ←  결제 API  ⚙      아바타 │   1행
│ [Bearer 토큰____________]  │   2행
└────────────────────────────┘
```

- Bearer는 **자리를 옮길 뿐 사라지지 않는다.**
- 헤더 높이는 모바일에서 커지지만(52px → 약 96px), 레이아웃이 flex로 배분하므로 문제되지 않는다.
- Dashboard · ProjectForm 헤더는 요소가 적어 모든 폭에서 1행 유지. 프로젝트명만 `truncate`.

**구현: `order` + `flex-wrap`.**
`hidden md:block`으로 DOM을 두 벌 렌더하지 **않는다** —
그러면 브레이크포인트를 넘을 때 입력값 · 포커스 · 커서가 날아간다.
같은 DOM 노드를 `order`로 재배치한다.

```
모바일:   [left ....... right]   order 1, 2
          [wide ............]   order 3, basis-full
데스크탑: [left ... wide  right] order 1, 2, 3
```

## 유저 드롭다운

아바타 클릭 시 열린다.

```
이름
이메일
──────────────
알림 목록 (미확인 우선 · 스크롤)
──────────────
테마 토글 (라이트 / 다크)
──────────────
로그아웃
```

**알림 개수 규칙**

- 미확인 > 5 → **미확인 전부** 표시 (리스트 영역 `max-height` + 스크롤)
- 미확인 ≤ 5 → 총 5개 (미확인 + 최근 확인분으로 채움)
- 미확인 0 → 최근 5개

미확인 알림이 있으면 아바타에 작은 빨간 점.

**테마 토글이 헤더가 아니라 드롭다운에 있는 이유**

테마는 한 번 정하면 거의 바꾸지 않는다. 상시 노출할 만큼 자주 쓰지 않으며,
헤더 아이콘을 하나 늘리면 SpecDetail 헤더가 더 붐빈다.

**비로그인(Login · Signup)에는 토글이 없다.**
헤더 자체가 없고, `ThemeContext`가 저장값이 없을 때 OS 설정(`prefers-color-scheme`)을 따르므로
다크 모드 사용자는 자동으로 다크 화면을 본다.

## 푸터

- 하단 고정(`fixed`). 작은 글씨.
- **배경 없음 · 투명 · `pointer-events-none`** — 아래 요소의 클릭을 막지 않는다.
- z-index는 높게. 링크는 두지 않는다(클릭이 통과하므로).
- 본문 하단에 푸터 높이만큼 여백을 확보해 콘텐츠가 가려지지 않게 한다.
- 정렬: Login·Signup은 **x축 중앙**, 나머지는 **x축 왼쪽**.

## 반응형 정책

**대응 범위: 데스크탑 + 모바일.** 태블릿용 별도 분기는 두지 않는다.
중간 폭은 브레이크포인트에 따라 자연스럽게 늘어난다.

| 화면                | 모바일 대응                                             |
| ------------------- | ------------------------------------------------------- |
| Login · Signup      | 이미 중앙 좁은 카드 — 그대로 작동                       |
| Dashboard           | 카드 그리드 `grid-cols-1 sm:grid-cols-2 lg:grid-cols-3` |
| ProjectForm         | 2열 폼 → 모바일 1열                                     |
| 헤더                | SpecDetail만 Bearer가 2행으로 (`md` 기준)               |
| 푸터                | 폭만 따라감 — 별도 대응 불필요                          |
| **SpecDetail 본문** | **3컬럼 유지 + 가로 스크롤**                            |

### SpecDetail 모바일에서 가로 스크롤을 택한 이유

"데스크탑에서 이용해 주세요" 같은 **차단 화면은 두지 않는다.**
알림 딥링크로 모바일에서 진입한 사용자가 내용을 아예 볼 수 없게 되는 것은
불편한 가로 스크롤보다 나쁘다. **불편해도 접근 가능한 쪽**을 택한다.

- 3컬럼 컨테이너에 최소 폭(`min-w-[900px]`)을 주고 부모에 `overflow-x-auto`.
- 헤더는 스크롤 컨테이너 밖이므로 가로로 밀리지 않는다(뷰포트 폭 유지).
- 사이드바 **드로어 전환은 후순위**. 3컬럼 셸이 안정된 뒤에 붙이는 편이 쉽고,
  붙이면 가로 스크롤을 대체한다.

## SpecDetail 스크롤 구조

**페이지 전체 스크롤은 없다. 각 컬럼이 따로 스크롤한다.**

```
h-dvh  flex flex-col
├── Header                            ← 자연 높이 (1행 52px / 모바일 2행 ~96px)
└── flex-1 min-h-0 overflow-x-auto    ← 남는 높이 전부 · 좁으면 가로 스크롤
    └── flex h-full min-w-[900px]
        ├── 왼쪽   w-[220px] shrink-0  overflow-y-auto  pb-8
        ├── 중앙   flex-1 min-w-0      overflow-y-auto  pb-8
        └── 오른쪽 w-[280px] shrink-0  flex flex-col    ← overflow 없음
            ├── 댓글 헤더
            ├── 목록  flex-1 min-h-0 overflow-y-auto pb-8
            └── 입력창                                  ← 바닥 고정
```

| 규칙                                            | 이유                                                                                                               |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `h-dvh` (not `h-screen`)                        | 모바일 브라우저의 `100vh`는 주소창을 포함한 값이라 실제 보이는 높이보다 크다. 그대로 쓰면 화면 아래가 잘린다.      |
| 높이를 `calc(100vh - 52px)`로 하드코딩하지 않음 | 헤더 높이가 모바일에서 2행(~96px)으로 바뀐다. flex가 남는 높이를 자동 배분하게 둔다.                               |
| 스크롤 컨테이너마다 `min-h-0`                   | flex 아이템의 기본 `min-height: auto` 때문에 콘텐츠보다 작아지지 않아 `overflow-y-auto`가 동작하지 않는다.         |
| 왼쪽 · 중앙 · 댓글목록에 `pb-8`                 | 하단 고정 푸터 글씨에 마지막 콘텐츠가 가리지 않도록.                                                               |
| 오른쪽 컬럼 자체엔 `overflow` 없음              | 컬럼 전체를 스크롤시키면 입력창이 함께 밀린다. 컬럼은 `flex flex-col`, **목록만** 스크롤하고 입력창은 바닥에 고정. |
| 입력창에는 `pb-8` 없음                          | 입력창은 바닥에 붙어 "여기가 끝"이라는 기준선이 된다. 푸터는 왼쪽이라 겹치지 않는다.                               |

### 컬럼 리사이즈

- **왼쪽 사이드바는 고정폭.** 엔드포인트 경로는 폭이 예측 가능하고, 넓힐 실익이 적다.
  경로가 길면 `truncate` + 툴팁으로 처리한다.
- **오른쪽 댓글 패널만 드래그 리사이즈.** `react-resizable-panels` 사용.
- **숨김 버튼은 없다.**
- 중앙은 `flex-1`로 남는 폭을 자동으로 차지한다 — 댓글 패널을 넓히면 중앙이 줄어든다.
