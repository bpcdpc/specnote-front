## 전제

### 데이터 흐름

| 시점            | 호출                                      | 받는 것                                             |
| --------------- | ----------------------------------------- | --------------------------------------------------- |
| 프로젝트 진입   | `GET /api/projects/:id`                   | `ProjectMeta` — 설정, 권한, title, latestSnapshotId |
| 진입, 새로고침  | `GET /api/projects/:id/spec?snapshotId=N` | `Spec` — info 메타, components, 전체 operation      |
| 엔드포인트 클릭 | 없음                                      | `spec.operations.find(...)`                         |

- **엔드포인트 클릭이 네트워크를 타지 않는다.** 목록과 상세가 같은 배열에서 나오므로
  둘의 버전이 갈릴 경로가 없다. 이것이 재설계의 요지다.
- `components`는 스펙 응답에 함께 온다. 엔드포인트마다 다시 받지 않는다.
- `$ref`는 dereference된 상태로 오지 않는다. 렌더 시점에 캐시에서 lazy resolve한다.
- `operations`는 소프트 삭제된 것을 **포함**한다. 필터링은 프론트 책임이다.
  단, 요청 스냅샷보다 나중에 생긴 삭제분은 서버가 뺀다(`10-api-specifications`).
- **메타의 `latestSnapshotId`가 스펙의 `snapshotId`보다 높으면** 그 사이 스펙이 갱신된 것이다.
  조용히 교체하지 않고 배너로 알린다(11-9). 판정 입력은 메타 폴링 하나다.

> 이 절의 상세한 규약(앵커, 쿼리 키, `staleTime`)은 `08-state-and-data`의 스펙 앵커 절.

### 라우트

프론트 URL은 중첩, 백엔드 라우트는 플랫이다. 서로 독립이며 충돌하지 않는다.

```
/projects/:projectId                          엔드포인트 미선택
/projects/:projectId/endpoints/:endpointId    선택됨
/projects/:projectId/endpoints/:endpointId?comment=:commentId   알림 딥링크
```

- 선택 상태의 소유자는 URL이다. 컴포넌트 state로 들지 않는다. 새로고침과 뒤로가기가 살아야 하고,
  알림 딥링크가 같은 경로를 그대로 쓴다.
- **자식 라우트 둘에 같은 엘리먼트(`SpecDetailPage`)를 매단다.** 페이지가
  `useParams().endpointId`를 직접 읽어 있으면 상세, 없으면 개요를 그린다.
  `<Outlet>`은 **3컬럼 전체**를 감싼다. 중앙 컬럼만 `<Outlet>`으로 만들면
  좌우 컬럼과 셸이 레이아웃에, 중앙만 라우트에 걸려 소유권이 흐려진다 — 그렇게 하지 않는다는
  뜻이지 자식 라우트 자체를 안 쓴다는 뜻이 아니다.
- `?comment=`는 11단계에서 읽지 않았다. 13단계에서 **`CommentPanel`** 이 읽는다 —
  이 폴더의 파일이지만 3컬럼 셸이 아니라 댓글 도메인 소관이다(`03-frontend-layouts`).

### 컬럼

| 컬럼   | 기본    | min | max | 리사이즈 | 접기 |
| ------ | ------- | --- | --- | -------- | ---- |
| 왼쪽   | 330px   | 240 | 400 | ✅       | ✅   |
| 중앙   | 남는 폭 | 320 | —   | —        | —    |
| 오른쪽 | 440px   | 240 | 600 | ✅       | ✅   |

`h-dvh` 고정, 페이지 스크롤 없음. 각 컬럼이 `overscroll-none`으로 독립 스크롤한다.

**`lg`(1024px) 분기** — `≥ lg`는 밀어내기(접으면 중앙이 넓어짐), `< lg`는 덮기
(양쪽 오버레이, 기본 닫힘, 하나만 열림, 백드롭/Esc). 기준은 **최소폭 합계**다 —
`240 + 320 + 240 + 구분선 2 = 802px`이고, `md`(768)로 가르면 768 < 802라 깨진다.
기본폭이 아니라 최소폭으로 잡아야 컬럼 폭을 조정해도 브레이크포인트가 흔들리지 않는다.

`min-w-[900px]` 가로 스크롤은 폐기했다. 차단 화면은 만들지 않는다. 상세는 `03-frontend-layouts`.

**치수와 여백은 `panelMetrics.ts`가 전담한다.** `SpecColumns`, `EndpointSidebar`,
`CommentPanel`, `SpecLayout`이 전부 여기서 값을 가져간다. 컴포넌트 안에 숫자를 직접 쓰지 않는다 —
헤더 우측 폭과 댓글 패널 내용 폭처럼 서로 맞아야 하는 값이 있어서다.
**위 표는 그 파일의 사본이므로 코드를 고치면 여기도 같이 고친다.**

#### `react-resizable-panels` v4 주의

v3 예제를 그대로 가져오면 전부 깨진다. 이름이 바뀌었다.

| v3                  | v4            |
| ------------------- | ------------- |
| `PanelGroup`        | `Group`       |
| `PanelResizeHandle` | `Separator`   |
| `direction` prop    | `orientation` |
| `tagName` prop      | 삭제됨        |

- v4는 **px 단위를 지원한다.** v3의 백분율 환산이 필요 없어 `minSize`, `maxSize`를
  디자인 값 그대로 적을 수 있다.
- 접기는 `collapsible` + `collapsedSize`로 선언하되, 여닫는 것은 패널 `ref`의
  명령형 API(`expand()`, `collapse()`, `isCollapsed()`)로 다룬다.
  헤더 토글이 상태를 갖고 패널이 그 상태를 따라가야 해서다.
- `expand()`는 "가장 최근 크기"로 되돌린다. 접었다 펴도 드래그한 폭이 유지된다.
- `Group`은 `relative` 패널을 **최소 하나** 요구한다. 양쪽 날개에
  `groupResizeBehavior="preserve-pixel-size"`를 주고 중앙은 기본값으로 둔다.
- `Panel` 안쪽 div에 `overflow:auto`가 인라인으로 이미 있고 `className`도 그 div로 간다.
  스크롤 주체가 그 div이므로 `overscroll-none`은 `Panel`의 `className`에 붙인다.

## 파일

`02-frontend-directories`의 목록에 재귀 렌더 2종을 추가한다.

```
pages/spec-detail/
├── SpecDetailPage.tsx        # 3컬럼 본문, endpointId 읽기
├── SpecColumns.tsx           # 3컬럼 셸 — 리사이즈 + 접기 + 오버레이
├── panelMetrics.ts           # 컬럼 폭, 여백, sticky 클래스
├── SpecPanelsContext.tsx     # 양쪽 패널 열림/접힘, isWide 공유
├── BearerTokenContext.tsx    # 헤더 입력값을 TryItPanel까지 전달
├── BearerTokenInput.tsx      # 헤더 Bearer 입력
├── ProjectOverview.tsx       # 엔드포인트 미선택 시 중앙
├── EndpointSidebar.tsx       # 검색 + 태그 그룹 + 삭제된 엔드포인트 보기
├── EndpointListItem.tsx      # 메서드 뱃지 + path
├── EndpointDetail.tsx        # parameters / requestBody / responses 조립
├── SchemaTree.tsx            # 스키마 재귀 노드
├── ExampleBlock.tsx          # example 값 표시
├── buildExample.ts           # 스키마 → 요청 바디 초기값 조립
├── useTryIt.ts               # 요청 조립, 전송, 응답 상태
├── TryItPanel.tsx            # 입력 → HTTP 요청 → 응답
├── SpecUpdateBanner.tsx      # snapshotId 불일치 배너
├── useSpecCache.ts           # components 캐시 + $ref 지연 해석
└── comments/                 # 12단계
```

목 데이터는 `pages/spec-detail/mock.ts`가 아니라 **`lib/mock.ts`** 로 갔다.
프로젝트 목록과 댓글까지 먹으면서 소비처가 여럿이 됐다. 배치 기준은
"소비처가 하나인가 여럿인가"이고 파일의 형태가 아니다(`02-frontend-directories`).
**배관 5로 소비처가 사라져 파일째 제거했다.** 아래 11-1은 그 시점의 기록이다.

**`SchemaTree`를 가르는 이유**: FR-4.3이 중첩 객체와 배열의 재귀 전개를 요구한다.
재귀 노드는 자기 자신을 부르는 단일 책임 컴포넌트라야 하고,
`EndpointDetail`은 parameters/requestBody/responses 세 구획을 배치하는 조립 책임만 진다.
한 파일에 두면 재귀 깊이 제어, 펼침 상태, 구획 배치가 뒤엉킨다.

### 11-1. 목 데이터

**근거**: 이후 전 단계가 이 데이터를 먹는다. 형태가 흔들리면 전부 다시 고친다.

- 프로젝트 진입 응답 1건, 엔드포인트 상세 여러 건.
- 실제 OAS 조각이어야 한다. `$ref`, 배열 안 중첩 객체, enum, 여러 응답 코드를 포함시킨다.
  단순한 flat 객체만 넣으면 11-5, 11-6이 검증되지 않는다.
- `tryItBaseUrl`이 `null`인 경우도 만든다. FR-4.5(비활성) 확인용.
- 소프트 삭제된 엔드포인트 최소 1건.

**완료 조건**: `lib/types.ts`의 타입에 캐스팅 없이 들어맞는다.

---

### 11-2. 3컬럼 골격

**근거**: 컬럼 안이 비어 있어도 폭, 스크롤 경계, 좁은 화면 동작을 먼저 고정해야
이후 컴포넌트가 자기 폭을 잘못 가정하지 않는다.

- `react-resizable-panels` **v4** 설치. 좌우 패널 모두 `Separator`를 갖는다.
- 스크롤 주체는 각 컬럼이다. 페이지 스크롤이 생기면 잘못된 것이다.
- `< lg`에서는 양쪽이 오버레이로 전환된다. 가로 스크롤은 쓰지 않는다.
- 패널 열림/접힘 상태와 `isWide`는 `SpecPanelsContext`가 갖는다.
  헤더의 토글 버튼과 3컬럼이 같은 상태를 봐야 하는데 둘의 소유자가 달라서다.

**완료 조건**: 창을 400px까지 줄여도 중앙이 읽히고 양쪽은 오버레이로 열린다.
세 컬럼이 각각 독립적으로 스크롤되고 끝에서 부모로 넘어가지 않는다.

---

### 11-3. 엔드포인트 사이드바

- 태그별 그룹핑. 태그가 없는 엔드포인트의 그룹명을 정해야 한다.
- 검색은 실시간 필터(FR-3.4). 대상은 path와 summary.
- 삭제된 엔드포인트는 기본 숨김, 토글로 노출하며 "삭제됨" 표시를 단다(FR-11.1).
  클릭하면 상세와 댓글은 그대로 열린다(FR-11.2).
- 메서드 뱃지는 `min-w-[52px]`로 path가 세로 정렬되게 한다.
- `method`는 백엔드가 `string`으로 준다. `isHttpMethod` 가드로 좁히고 벗어나면 폴백한다.

**완료 조건**: 검색어 입력 시 목록이 즉시 좁혀지고, 삭제됨 토글이 동작한다.

---

### 11-4. 라우트 배선

- 라우터에 `/projects/:projectId/endpoints/:endpointId`를 추가한다.
- 사이드바 항목은 버튼이 아니라 `<Link>`다. 새 탭 열기가 동작해야 한다.
- `endpointId`가 없으면 중앙 컬럼은 빈 상태를 렌더한다.
- 존재하지 않는 `endpointId`의 처리 방식을 정한다.

**완료 조건**: 항목 클릭 시 URL이 바뀌고, 새로고침해도 같은 엔드포인트가 열린다.
뒤로가기로 이전 선택으로 돌아간다.

---

### 11-5. 스펙 캐시

- `components`를 받아 `$ref` 문자열을 실제 스키마로 해석한다.
- **순환 참조 가드가 필수**다. 자기 자신을 참조하는 스키마에서 무한 재귀로 죽는다.
- 해석 실패(없는 `$ref`)를 예외로 던지지 않는다. 화면 한 칸만 깨지게 하고 나머지는 렌더한다.
- 3.0과 3.1의 `$ref` 형태 차이를 확인한다.

**완료 조건**: 중첩 `$ref`가 두 단계 이상 걸린 목 데이터에서 최종 스키마가 나온다.
순환 참조 목 데이터에서 멈추지 않는다.

### 11-6. 엔드포인트 상세

가장 크다. 세 구획으로 나눈다.

| 구획        | 내용                                                     |
| ----------- | -------------------------------------------------------- |
| parameters  | path / query / header, 이름, 타입, required, description |
| requestBody | content type별 스키마, example                           |
| responses   | 상태 코드별 스키마, example                              |

- `SchemaTree`는 자기 자신을 부른다. 객체는 properties로, 배열은 items로 내려간다.
- 깊이가 깊어지면 기본 접힘 처리를 할지 정한다.
- `ExampleBlock`은 스펙의 example, 없으면 스키마에서 생성할지 정한다.

**완료 조건**: 배열 안 중첩 객체가 재귀적으로 펼쳐진다(FR-4.3).

---

### 11-7. Bearer 토큰 입력

- `SpecLayout`이 헤더 `right` 슬롯에 조립한다. 페이지가 헤더를 건드리지 않는다.
- `< lg`에서 `wide` 슬롯으로 2행. `order` + `flex-wrap`으로 처리하고 DOM을 두 벌 렌더하지 않는다.
- 로그인 상태와 무관하게 항상 표시한다.
- 값은 `useState`로만 들고 저장소에 두지 않는다. 새로고침하면 사라진다(Swagger UI와 동일).
  SpecNote는 대상 API와 무관한 제3 서비스라 타 시스템의 API 토큰을 보관할 이유가 약하다.

**완료 조건**: 1024px 이상 1행, 미만 2행으로 전환되며 입력값이 유지된다.

---

### 11-8. Try it out

유일하게 실제 네트워크를 쓴다. 마지막에 둔다.

- `tryItBaseUrl`이 없으면 비활성. 이때도 열람과 댓글은 정상 동작한다(FR-4.5).
- POST/PUT/PATCH/DELETE는 전송 전 "실제 서버 데이터가 변경될 수 있음" 확인을 받는다.
  GET에는 표시하지 않는다(FR-4.9). 확인 방식은 체크박스이며 엔드포인트를 옮기면 초기화된다.
- 요청 폼의 초기값은 example이며 수정 가능하다(FR-4.4).
- 인증은 http bearer만 지원한다. 그 외(oauth2 등)는 미지원 안내.
- 실패 시 CORS 원인을 구분해 안내한다(FR-4.6). 브라우저는 CORS 실패를 일반 네트워크 오류와
  구분해 알려주지 않으므로, 상태 코드 없는 실패에 한해 가능성으로 안내한다.
- 응답은 상태 코드와 바디를 그대로 보여준다.

**완료 조건**: baseUrl 없는 프로젝트에서 비활성이고, 변경 계열 메서드에 경고가 뜬다.

---

### 11-9. 스펙 갱신 배너

- **메타의 `latestSnapshotId` > 지금 보고 있는 스펙의 `snapshotId`면 표시한다.**
  같거나 낮으면 표시하지 않는다.
- 조용히 교체하지 않는다. 사용자가 새로고침을 눌러야 반영된다.
- 배너를 닫은 스냅샷을 기억한다. 그보다 더 새 스냅샷이 오면 다시 뜬다.
- WebSocket 실시간 푸시는 스코프 밖이다.

**`≠`가 아니라 `>`인 이유**: 두 방향의 의미가 다르다.
`서버 최신 > 내 앵커`는 그 사이 커밋이 있었던 것이라 사용자가 새로고침을 눌러야 풀린다.
반대 방향은 오너가 커밋 직후 앵커를 먼저 당긴 순간에만 잠깐 생기고, 메타 폴링이
따라오면 저절로 맞는다 — 사용자에게 물을 것이 없다. `≠`로 두면 그 사이에 배너가
떴다 사라진다.

**완료 조건**: 다른 사용자가 커밋한 뒤 30초 안에 배너가 뜨고, 화면 내용은 그대로 유지된다.

## 결정 대기 → 결론

11단계 착수 시점에 미뤄뒀던 5건은 아래처럼 정했다.

| 단계 | 결정할 것                     | 결론                                           |
| ---- | ----------------------------- | ---------------------------------------------- | --- | ---- | ------------------- | --------------------------------- |
| 11-3 | 태그 없는 엔드포인트의 그룹명 | `Tag 없음`, 목록 맨 아래                       |
| 11-4 | 없는 `endpointId` 처리        | 중앙만 "찾을 수 없음", 사이드바는 그대로 유지  |     | 11-6 | 재귀 깊이 기본 접힘 | 2단계까지 펼침 (`OPEN_DEPTH = 2`) |
| 11-6 | example 자동 생성             | 요청 바디만 조립, 응답은 스펙에 있을 때만      |
| 11-7 | Bearer 토큰 보관              | `useState`. 저장소 없음, 새로고침하면 사라진다 |

- **없는 `endpointId`에 404 페이지를 띄우지 않는 이유**: 사이드바가 살아 있으면
  사용자가 바로 다른 엔드포인트로 갈 수 있다. 전체 화면 404는 탈출 경로를 없앤다.
- **`OPEN_DEPTH = 2`**: 1단계만 펼치면 대부분의 스키마에서 아무것도 안 보이고,
  3단계 이상이면 재귀 스키마에서 화면이 통째로 길어진다.

## 구현하며 확정된 설계 근거

- **순환 감지 책임 분리** — `$ref` 체인의 순환은 `useSpecCache`가, 구조적 순환(스키마가
  자기 자신을 properties로 갖는 경우)은 `SchemaTree`가 본다. 한쪽에 몰면 캐시가
  렌더 깊이를 알아야 하거나 트리가 해석 경로를 알아야 한다.
- **Try it 입력을 본문에 통합** — Swagger UI처럼 "Try it out" 모드 토글을 두지 않는다.
  토글을 두면 읽기용 `SchemaTree`와 입력용 `SchemaTree`를 두 벌 만들게 된다.
- **파라미터는 `SchemaTree`를 쓰지 않는다** — 거의 항상 스칼라라 재귀가 불필요하다.
  `enum`은 select, `boolean`은 true/false, 나머지는 단일 입력으로 평면 렌더한다.
- **엔드포인트 전환 시 리마운트** — `useEffect`로 상태를 동기화하는 것보다 안전하다.
  펼침 상태, 입력값, 응답이 전부 한 번에 초기화된다.

## 배관 4 이후 달라진 것

목 데이터를 실 API로 교체하면서 이 문서의 산출물 셋이 바뀌었다.
**이 중 일부는 아래 "재설계 이후 달라진 것"에서 다시 바뀌었다.** 시점 순으로 남긴다.

**프로젝트 조회를 `SpecLayout`이 갖는다.** 페이지가 아니다. 자식 라우트 둘이 같은
페이지 컴포넌트이고 둘 다 같은 데이터를 요구해서, 페이지에 두면 로딩과 에러 분기가
두 벌 생기고 `useSpecCache`가 `components` 없이 한 번 만들어졌다 버려진다.
레이아웃이 조회하고 `<Outlet context>`로 내린다(`03-frontend-layouts`).

**중앙 컬럼이 3상태에서 5상태가 됐다.** 11-4의 "없는 `endpointId`" 결론은 그대로
유지되고, 404 응답과 형식이 잘못된 URL이 같은 화면으로 수렴한다.
(상태의 구성은 재설계로 다시 바뀌었다.)

**리마운트 key가 `detail.id`에서 `${detail.id}-${detail.snapshotId}`로 바뀌었다.**
스펙이 커밋되면 같은 엔드포인트 id로 새 `operationJson`이 온다. id만 보면 key가 안 바뀌어
Try it 입력값이 옛 스키마 기준으로 남는다. 리로드가 전부 초기화하던 종전 동작과 같아진다.

**`getMockEndpointDetail`의 참조 안정성 문제는 사라졌다.** 목에서는 호출할 때마다 새 객체를
만들면 재귀 트리의 memo가 전부 무효화돼서 `DETAIL_CACHE`로 같은 참조를 돌려줬다.
TanStack Query는 structural sharing이 기본이라 내용이 같은 refetch에서 참조를 유지한다.
`useSpecCache`도 `components` 참조가 그대로면 재구축되지 않는다.

**배너 새로고침이 `window.location.reload()`가 아니다.** 리로드는 Bearer 토큰(`useState`)과
패널 폭, 펼침 상태까지 날린다 — 갱신 대상은 스펙이지 화면 상태가 아니다.
(무효화로 처리하던 방식은 재설계에서 앵커 이동으로 바뀌었다.)

---

## 재설계 이후 달라진 것

스펙 조회를 스냅샷 단위 단일 응답으로 재편하면서 이 문서의 전제가 바뀌었다.
**11-1~11-8의 산출물은 그대로 살아 있다.** 사이드바, `SchemaTree`, `useSpecCache`,
Try it은 받는 데이터의 출처만 달라졌을 뿐 하는 일이 같다.

**엔드포인트 클릭이 요청을 만들지 않는다.** 11-4의 라우트 배선은 그대로지만,
`endpointId`로 하는 일이 조회가 아니라 `spec.operations.find()`가 됐다.
사이드바 목록과 중앙 상세가 같은 배열에서 나오므로 둘의 버전이 갈릴 수 없다.

**중앙 컬럼 5상태의 구성이 바뀌었다.** 로딩과 실패가 레이아웃으로 올라가 사라지고,
그 자리에 "앵커 스펙에 없음"과 "존재하지 않음"이 들어왔다. 둘을 가르는 것은
배너 표시 여부(`outdated`)다 — 배너가 떠 있으면 "새로고침하면 표시됩니다",
아니면 "찾을 수 없습니다"다.

옛 구조에서 서버가 `NOT_IN_SNAPSHOT` 코드로 알려주던 상황이 이것이다. 서버 분기는
사라졌지만 **상황은 남는다** — 알림 딥링크로 커밋 이후에 생긴 엔드포인트에 도착하는
경로가 그대로다. 판정 근거만 응답 코드에서 `outdated`로 옮겨갔다.

**배너 새로고침이 앵커 이동 하나다.** `invalidateQueries`를 부르지 않는다.
앵커가 쿼리 키에 들어가 있어 키가 바뀌면 스펙 전체가 따라온다. 무효화 순서를
맞출 일이 없어졌고, 리로드가 아니므로 Bearer 토큰과 패널 폭도 살아남는다.

**배너와 `dismissed`의 소유자가 `SpecLayout`이다.** 페이지에 두면 개요와 상세가
다른 라우트라 이동할 때마다 닫은 배너가 되살아난다. 올리면서 개요 화면에서도
배너가 뜨는 요구(FR-10.6)가 함께 해결됐다.

**리마운트 key는 그대로 `${id}-${snapshotId}`다.** 근거도 같다. 값의 출처가
상세 응답에서 `spec.snapshotId`로 바뀌었을 뿐이다.

## 13단계 이후 달라진 것

**댓글 패널이 URL 쿼리스트링을 읽는다.** 11-4에서 "선택 상태의 소유자는 URL"이라고 정한
범위가 `?comment=`까지 넓어졌다. 읽는 주체는 `CommentPanel`이고, 값을
`CommentProvider`의 초기 하이라이트로 넘긴 뒤 파라미터를 뗀다.
3컬럼 셸(`SpecColumns`)과 `SpecDetailPage`는 이 값을 모른다 —
하이라이트가 댓글 도메인 상태라서다(`03-frontend-layouts`).

**좁은 폭에서 딥링크가 도착하면 댓글 패널을 연다.** 덮기 모드의 기본은 닫힘인데,
슬롯 자체는 렌더되므로 하이라이트가 화면 밖에서 뜨고 스스로 꺼진다.
`SpecPanelsContext`의 `setCommentsOpen`을 `CommentPanel`이 부른다 —
패널 상태를 화면 밖에서 건드리는 유일한 경로다.
