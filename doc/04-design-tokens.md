## 원칙

- **색을 아낀다.** 위계는 보더 + 텍스트 3단계 + 여백으로 만든다.
- **면을 나누지 않는다.** 페이지와 카드가 같은 색이고, 구분은 **보더**가 전담한다.
- **CTA는 파랑이 아니라 무채색 채움**이다.

| 파랑을 쓴다            | 파랑을 쓰지 않는다 |
| ---------------------- | ------------------ |
| 입력 포커스 링         | CTA · primary 버튼 |
| 링크                   | 아바타             |
| 선택된 항목 표시       | 보조 · 아이콘 버튼 |
| OWNER 뱃지 · 본인 뱃지 | 카드 강조          |

화면당 파란 요소 몇 개(카드 목록의 OWNER 뱃지 등)는 허용한다. 금지가 아니라 남발 금지다.

**멘션은 파랑이 아니다.** v0.5까지 "링크와 멘션은 파랑"이었으나 12단계에서 뒤집었다.
댓글 본문 안에서 멘션 칩이 파랑이면 같은 화면의 선택 표시, OWNER 뱃지, 포커스 링과
같은 색이 되어 "파랑 = 시스템이 강조한 것"이라는 규칙이 흐려진다. 멘션은 사용자가
남긴 것이므로 다른 계열이 맞다. 값은 아래 "댓글" 절.

## 표면 · 텍스트

| 용도                         | 라이트    | 다크      |
| ---------------------------- | --------- | --------- |
| 표면 1 (카드 · 헤더 · 패널)  | `#ffffff` | `#000000` |
| 표면 2 (페이지 배경)         | `#ffffff` | `#000000` |
| 표면 3 (선택된 항목)         | `#f2f2f2` | `#242424` |
| 호버 (ghost, 카드, 드롭다운) | `#f4f4f4` | `#1c1c1c` |
| 호버 (아이콘 버튼, 목록 행)  | `#ebebeb` | `#212121` |
| 텍스트 1 (본문)              | `#171717` | `#ededed` |
| 텍스트 2 (보조)              | `#666666` | `#a1a1a1` |
| 텍스트 3 (흐림 · 캡션)       | `#8f8f8f` | `#737373` |
| 보더                         | `#cbcbcb` | `#313131` |
| 보더 (인풋)                  | `#d4d4d4` | `#303030` |
| 보더 (인풋 포커스)           | `#8f8f8f` | `#737373` |
| 배경 (인풋)                  | `#fafafa` | `#000000` |

- **표면 1 = 표면 2다.** 토큰을 둘로 유지하는 건 나중에 다시 갈라야 할 때 컴포넌트를 안 고치기 위해서다.
- 다크 본문은 순백이 아닌 `#ededed`. 순수 블랙 위의 순백은 대비가 과하다.
- 인풋은 버튼 보더보다 옅은 전용 보더를 쓴다. 다크 배경은 표면과 같은 순검정이라
  구분은 보더가 전담한다.
- **인풋 포커스는 전용 토큰이다.** v0.4의 "포커스 시 `--border` 색으로 진해진다"는
  실제 구현과 달랐다. `--sn-input-border-focus`가 따로 있고 평상시 보더보다 두 단 밝다.
  일반 보더를 그대로 쓰면 인풋이 여럿 놓인 폼에서 포커스 여부가 잘 안 읽힌다.
- **접근성을 보더의 근거로 쓰지 않는다.** WCAG 1.4.11은 UI 컴포넌트 경계에 3:1을
  요구하는데, 다크의 `#313131`은 순검정 대비로 여기에 미달한다. v0.4~v0.5에서 보더를
  두 차례 올린 것은 **시각적으로 너무 약했기 때문**이지 기준을 맞추려던 게 아니다.
  통과시키려면 더 밝은 회색이 필요하고 그러면 화면이 상자투성이가 된다. 미달을
  의도적으로 감수하는 상태이며, 접근성 문구로 정당화하지 않는다.
  포커스 링(파랑)은 이 대비와 무관하게 별도로 작동한다.

## 강조 — Vercel Blue 3단계

| 단계         | 유틸                                        | 라이트    | 다크      | 쓰는 곳                     |
| ------------ | ------------------------------------------- | --------- | --------- | --------------------------- |
| subtle(흐림) | `bg-accent-subtle`                          | `#e8f0fe` | `#10243f` | 뱃지 · 태그 배경            |
| muted(중간)  | `text-accent-muted` `bg-accent-muted`       | `#7aa7f0` | `#2d5a9e` | 보조 강조                   |
| strong(원색) | `text-accent-strong` `border-accent-strong` | `#0070f3` | `#0070f3` | 글자 · 아이콘 · 보더 · 링크 |
| hover        | `text-accent-hover`                         | `#0060d9` | `#3291ff` | 강조 요소 hover             |

원색은 라이트·다크가 같고 hover만 방향이 반대다(밝은 배경에선 어둡게, 어두운 배경에선 밝게).

**뱃지 패턴** — OWNER 뱃지, 본인 뱃지가 공유한다.

```
rounded-full bg-accent-subtle text-accent-strong
px-2.5 py-0.5 text-[10px] font-semibold tracking-wide
```

## 메서드 뱃지

**라이트는 솔리드(색 배경 + 흰 글자), 다크는 색 글자 + 같은 색 10% 배경.**
v0.4의 "박스 없음, 컬러 텍스트만" 방침은 폐기했다. 목록에서 메서드가 세로로 늘어설 때
컬러 텍스트만으로는 스캔이 안 되고, 짧은 이름(GET)과 긴 이름(DELETE)의 무게가 어긋난다.

| 메서드 | 라이트(배경) | 다크(글자) |
| ------ | ------------ | ---------- |
| GET    | `#067a2e`    | `#00cf39`  |
| POST   | `#0066cc`    | `#00a4ff`  |
| PUT    | `#007a78`    | `#00f1f0`  |
| PATCH  | `#9a3beb`    | `#d16eff`  |
| DELETE | `#d6006a`    | `#ff358d`  |

- 라이트 = 위 색을 배경으로 깔고 글자는 흰색.
- 다크 = 위 색을 글자로 쓰고 배경은 **같은 색 15% 알파**(`#00cf3926` 형태의 8자리 hex).
  순검정 위에서 솔리드는 너무 튄다.
- `border-*` 토큰은 값을 `transparent`로 두고 **선언은 남겨뒀다.** 배경이 있으면 보더가
  이중선이 되므로 쓰지 않는다. 지운 게 아니라 끈 것이라, `MethodBadge`의 클래스
  목록은 그대로 두고 값만 되살리면 언제든 보더 방식으로 되돌릴 수 있다.
- **가운데 정렬**한다. 솔리드 박스에서 왼쪽 정렬이면 GET처럼 짧은 메서드가 왼쪽에 쏠려 보인다.
- 뱃지 폭은 `min-w-[52px]`로 맞춰 목록에서 경로가 세로 정렬되게 한다.
- `MethodBadge`에 분기가 없다. CSS 변수만 참조하고 `.dark`에서 값만 바뀐다.

### 대소문자

**저장값은 소문자, 표시만 대문자다.**
OAS Path Item Object의 키가 소문자이고 `spec-extractor`가 그대로 저장한다.
뱃지가 `uppercase` 클래스로 표시할 때만 올린다. 호출부에서 `toUpperCase()`를 부르지 않는다.

### `FallbackBadge`

`head` / `options` / `trace` 등 5종 밖의 메서드는 **무채색**으로 렌더한다.

```
bg-surface-3 text-fg-2
```

관례가 없는 메서드에 임의로 색을 주면 5종의 색 규칙이 흐려진다.
"이 색은 무슨 뜻인가"에 답할 수 없는 색은 넣지 않는다.
좁히기 규칙(`isHttpMethod` 가드로 갈라 폴백)은 `05-code-conventions`.

### 업계 관례와 어긋나는 두 곳

- **PUT 시안** — Swagger UI는 주황이다.
- **PATCH 보라** — Swagger UI는 민트다.

색상환에서 5종이 고르게 벌어지는 배치를 우선했다. GET 초록, POST 파랑, DELETE 빨강은
관례를 따르므로 오독 위험이 큰 세 개는 지켜진다. 관례를 어긴 것은 의도이며,
다르게 보인다는 지적이 들어오면 이 항목을 근거로 재논의한다.

## 버튼

**기본은 outline이고, CTA만 채운다. 채움은 파랑이 아니라 무채색이다.**

| 종류        | variant       | 스타일                                                        | 쓰는 곳                  |
| ----------- | ------------- | ------------------------------------------------------------- | ------------------------ |
| CTA         | `default`     | 다크=흰 채움/검은 글자, 라이트=검은 채움/흰 글자. hover `/80` | 화면의 주 액션, 보통 1개 |
| 보조        | `outline`     | 보더만. 배경 없음. hover 시 배경 옅게                         | 그 외 텍스트 버튼        |
| 아이콘 버튼 | (직접 스타일) | 보더·배경 없음. hover 시 `--sn-hover-icon` 배경               | `←` `⚙` `✕` 등           |

- CTA hover는 별도 색이 아니라 **불투명도**(`bg-primary/80`)다. 배경이 비쳐 톤이 뜨고,
  라이트/다크에 hover 색을 따로 정의할 필요가 없다.
- 컨트롤 높이는 **`h-10`(40px)** 통일. 버튼과 인풋이 같아야 나란히 놓았을 때 안 어긋난다.
  화면의 주인공이 되는 입력(프로젝트 생성의 스펙 URL)만 그 화면에서 `h-12`.
- 아이콘 버튼은 보더를 두지 않는다(v0.3의 outline 방침을 뒤집음). 포커스 링만 유지.
- 버튼에 `cursor: pointer`를 넣지 않는다 — 네이티브 커서를 따른다(Base UI · shadcn 기본).

> **구현**: `components/ui/button.tsx` — `size.default`를 `h-10 px-3`으로,
> 공통 radius `rounded-md`, `outline` variant의 기본 배경 제거(`bg-transparent`,
> 다크 `bg-input/30` 삭제).

**hover 배경 2단계**

| 토큰               | 용도                         | 라이트    | 다크      |
| ------------------ | ---------------------------- | --------- | --------- |
| `--sn-hover-ghost` | ghost 버튼 · 카드 · 드롭다운 | `#f7f7f7` | `#141414` |
| `--sn-hover-icon`  | 아이콘 버튼 · 목록 행        | `#f0f0f0` | `#1a1a1a` |

**링크로 이동하는 버튼**

`Button`을 쓰지 말고 `<Link>`에 버튼 스타일을 직접 입힌다. 의미상 `<a>`가 맞고,
Base UI는 `render`에 `<a>`를 넘기면 `nativeButton` 경고를 낸다(`05-code-conventions`).

```tsx
<Link
  to="/projects/new"
  className="inline-flex h-10 items-center gap-1.5 rounded-md bg-primary px-3
             text-sm font-medium text-primary-foreground hover:bg-primary/80"
>
  새 프로젝트
</Link>
```

## 인풋

| 항목    | 값                                                              |
| ------- | --------------------------------------------------------------- |
| 높이    | `h-10` (버튼과 동일)                                            |
| radius  | `rounded-md` (6px)                                              |
| 보더    | `border-input-border` — 버튼 보더보다 옅게, **항상 표시**       |
| 배경    | `bg-input-bg` — 아주 옅게                                       |
| 포커스  | **링 없음.** `border-input-border-focus` 전용 토큰으로 밝아진다 |
| invalid | 보더만 `--destructive`. 링 없음                                 |

링(ring)은 요소 바깥으로 번져 촘촘한 폼에서 서로 간섭한다. 보더 색만 바꾸면
레이아웃이 흔들리지 않고 변화도 충분히 읽힌다.

> **구현**: `components/ui/input.tsx` — `h-10`, `rounded-md`,
> 전용 토큰(`border-input-border` `bg-input-bg`), 포커스 링 제거 후
> `focus-visible:border-input-border-focus`.

댓글 에디터는 `Input`이 아니라 `textarea`를 직접 쓰지만 같은 토큰을 따른다.
포커스는 요소 자신이 아니라 바깥 래퍼가 `focus-within:border-input-border-focus`로 받는다.
툴바와 하단 바가 같은 테두리 안에 들어가야 한 덩어리로 보이기 때문이다.

## radius

| 토큰                        | 값   | 적용                    |
| --------------------------- | ---- | ----------------------- |
| `--radius-sm` `--radius-md` | 6px  | 버튼 · 인풋 · 목록 행   |
| `--radius-lg` `--radius`    | 8px  | —                       |
| `--radius-xl`               | 12px | 카드                    |
| `rounded-full`              | 원형 | 아바타 · 뱃지 · 멤버 칩 |

v0.2의 "전부 3px"을 폐기했다. 컨트롤과 카드의 곡률이 같으면 위계가 안 생긴다.

> **확인 필요**: `index.css`의 `--radius-md`가 `0.365rem`으로 들어가 있다.
> `--radius-sm`이 `0.375rem`(6px)이므로 오타로 보인다. 5.84px과 6px은 눈으로
> 구분되지 않아 화면에는 드러나지 않지만, 값이 둘로 갈린 상태다.

## 다크 모드

`<html>`에 `.dark` 클래스를 붙였다 뗀다(shadcn 표준). `ThemeContext`가 토글하고
`localStorage`에 저장한다. 저장값이 없으면 OS 설정을 따른다.

```css
@custom-variant dark (&:where(.dark, .dark *));

:root { --sn-surface-1: #ffffff; ... }
.dark { --sn-surface-1: #000000; ... }
```

색은 전부 `--sn-*`로 두고 `.dark`에서 **값만 교체**한다. 컴포넌트는 `bg-surface-1` 하나만 쓰고
다크 대응을 따로 하지 않는다.

**라이트 모드를 빼지 않는다.** 컴포넌트에 `dark:` 분기가 없는 현 구조에서 라이트 유지 비용은
거의 0이다. 값 튜닝이 번거로우면 튜닝을 미루되 구조는 건드리지 않는다.

## 댓글 (12단계)

### 리액션

값(`REACTION_TYPE`)은 백엔드와 공유하지만 **표시는 프론트가 정한다.**
정의 위치는 `pages/spec-detail/comments/reactions.ts`.

| 값         | 이모지 | 라벨    |
| ---------- | ------ | ------- |
| `DONE`     | ✅     | 처리됨  |
| `CHECKING` | 👀     | 확인 중 |
| `BEST`     | 👍     | 최고    |
| `ACK`      | 👌     | 알겠음  |

**이모지를 쓰는 것은 "색을 아낀다" 원칙의 예외다.** 리액션은 색 자체가 정보를
나르는 자리다. GitHub, Slack 등에서 리액션은 이모지가 관습이고, 단색 아이콘보다
뜻이 즉각 읽힌다. 무채색 아이콘 4종으로는 "처리됨"과 "알겠음"이 구분되지 않는다.

표시 순서는 `constants.ts`의 `REACTION_TYPES` 배열 순서를 그대로 따른다.
문서나 컴포넌트에서 따로 정하면 값이 늘거나 순서가 바뀔 때 고칠 곳이 둘이 된다.

- 달린 리액션만 칩으로 그린다. 4종을 항상 다 그리지 않는다.
  패널 최소폭 240px에서 좌우 여백을 빼면 176px이고, 빈 칩 4개가 늘 자리를 차지하면
  목록이 시끄럽다.
- 내가 단 칩은 `bg-accent-subtle text-accent-strong`, 아닌 것은 `text-fg-2`.
- 삭제된 댓글에도 리액션은 그대로 붙는다(FR-5.3).

### 멘션 칩

**amber를 쓴다. 파랑이 아니다.** 근거는 위 "원칙" 절.

| 모드   | 배경              | 글자                |
| ------ | ----------------- | ------------------- |
| 라이트 | `bg-amber-500/12` | `text-amber-700`    |
| 다크   | 배경 없음         | `text-amber-400/80` |

- 팀원 멘션과 엔드포인트 멘션이 **같은 톤**이다. "멘션은 이 모양"이라는 규칙 하나만 남긴다.
- 엔드포인트 멘션에 메서드 뱃지를 쓰지 않는다. 본문 문장 안에 색 박스가 끼면 문장이 끊긴다.
- 팀원 멘션은 링크가 아니라 `<span>`이다. 갈 곳이 없다 — 알림 발송이 목적이라 표시만 한다.
- Tailwind 기본 팔레트를 직접 쓰는 몇 안 되는 자리다. `--sn-*` 토큰으로 올리지 않은 이유는
  쓰이는 곳이 댓글 본문 한 군데뿐이라, 토큰으로 만들면 전역 팔레트에 의미 없는 항목이 는다.

### 굵기를 쓰지 않는다

댓글 본문의 `strong`과 `em`은 markdown 파싱은 통과시키되 **아무 스타일도 주지 않는다.**
좁은 패널에서 굵은 글자가 섞이면 작성자 이름보다 무거워 보여 위계가 뒤집힌다.
태그 자체를 막지 않는 이유는, 막으면 `**` 별표가 그대로 노출되기 때문이다.
굵은 글자보다 지저분하다.

### 새 댓글 하이라이트

```css
@keyframes comment-highlight {
  from {
    background-color: var(--color-accent-subtle);
  }
  to {
    background-color: transparent;
  }
}
```

방금 등록한 댓글을 2초에 걸쳐 배경에서 뺀다. 목록 정렬이 오름차순(오래된 게 위)이라
새 항목이 맨 아래에 붙는데, 스크롤만으로는 여러 항목 중 무엇이 방금 것인지 알 수 없다.
13단계 알림 딥링크가 같은 애니메이션을 재사용한다.
