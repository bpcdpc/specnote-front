## 공용으로 올리는 기준

`02-frontend-directories`의 기준("소비처가 하나인가 여럿인가")이 1차다.
그것만으로 안 갈리는 경우가 둘 있다.

**빠뜨리면 조용히 깨지는 속성이 있을 때.** 아이콘 전용 버튼의 `aria-label`이 그렇다.
빠져도 화면은 멀쩡하고 아무도 모른다. 필수 prop으로 만들어 컴파일이 잡게 한다.

**두 개 중 하나를 골라야 하는데 이름이 비슷할 때.** 호버 토큰이 `--sn-hover-ghost`와
`--sn-hover-icon` 둘이다. 화면마다 클래스를 손으로 쓰면 절반은 틀린다.

둘 다 "재사용을 위해"가 아니라 "틀릴 여지를 없애려고" 올리는 경우다.

## heading 계층

문서 아웃라인을 위해 제목 요소를 고정한다. **스타일이 아니라 의미로 정한다.**

| 레벨 | 무엇                   | 어디                                                  |
| ---- | ---------------------- | ----------------------------------------------------- |
| `h1` | 로고 `{SpecNote}`      | `Logo` (Login, Signup)                                |
| `h1` | 브레드크럼 마지막 조각 | `Breadcrumb` (모든 헤더)                              |
| `h2` | 화면 상단 제목         | `PageHeading` (모든 사용처)                           |
| `h2` | 엔드포인트 경로        | `SpecDetailPage` 중앙 컬럼 상단                       |
| `h3` | 목록 아이템 제목       | `ProjectCard` 등                                      |
| `h3` | 화면 내 구획 제목      | Parameters / Request Body / Responses, 댓글 패널 헤더 |

- `<span>`으로 제목처럼 보이게 하지 않는다. 스크린 리더가 heading 목록으로 탐색한다.
- 장식용 아이콘에는 `aria-hidden="true"`를 붙인다.
- **같은 컴포넌트가 제목일 때와 장식일 때가 갈리면 렌더 태그를 prop으로 받는다.**
  `Logo`의 `as="h1" | "span"`이 그 예 — 푸터 로고는 장식이므로 `span`이다.
- **`h1`은 화면당 하나다.** SpecDetail에서 브레드크럼의 프로젝트명이 `h1`이므로
  엔드포인트 경로는 `h2`다. 글자가 더 크다고 `h1`로 올리지 않는다.
- 댓글 한 건은 `<article>`이다. 제목 요소가 없고 작성자 이름은 `<header>` 안의 `<span>`이다 —
  이름은 제목이 아니라 메타데이터다.

## `IconButton`

아이콘만 있는 정사각 버튼. `⚙`, `✕`, 패널 토글, 댓글 액션 등이 쓴다.

```tsx
<IconButton
  label="엔드포인트 목록"
  onClick={toggleSidebar}
  aria-pressed={sidebarOpen}
>
  <PanelLeft />
</IconButton>
```

**`label`이 필수 prop이다.** 아이콘 버튼은 텍스트가 없어 접근성 이름이 없으면
스크린 리더가 "버튼"이라고만 읽는다. 화면에는 아무 이상이 없어서 리뷰로도 안 잡힌다.
필수로 만들어 타입 검사가 대신 잡게 한다. `aria-label`과 Tooltip 양쪽에 쓰인다.

**Tooltip을 내장한다.** 아이콘만으로 뜻이 안 읽히는 경우가 대부분이라
호버 설명을 컴포넌트가 책임진다. 화면마다 `Tooltip`으로 감싸는 것을 잊지 않게 한다.

**호버 배경은 `--sn-hover-icon`이다.** ghost 버튼과 카드가 쓰는 `--sn-hover-ghost`보다
한 단 진하다. 아이콘 버튼은 면적이 작아 같은 값이면 호버가 안 읽힌다.

- 기본 크기는 `size-8`(32px). 컨트롤 높이(`h-10`)와 다르다 — 헤더에 나란히 설 때
  아이콘 버튼이 텍스트 버튼만큼 커지면 헤더가 무거워진다.
  댓글 액션처럼 더 작아야 하는 자리는 `size="icon-xs"`.
- 보더와 배경은 없다. 포커스 링만 유지한다(`04-design-tokens`).
- **토글이면 `aria-pressed`를 준다.** 패널 토글이 이 경우다.

### `ICON_BUTTON_OVERRIDE` — Popover 트리거일 때

**`PopoverTrigger`의 자식으로 `IconButton`을 쓰면 팝오버가 안 열린다.**
내장 Tooltip과 `PopoverTrigger`가 같은 `Button`을 두고 다툰다.

이럴 때는 `Button` + `ICON_BUTTON_OVERRIDE`로 스타일만 맞춘다.

```tsx
<PopoverTrigger
  render={
    <Button
      variant="ghost"
      size="icon"
      aria-label="댓글 전체 이동"
      className={ICON_BUTTON_OVERRIDE}
    >
      <CornerUpRight className="size-4" aria-hidden="true" />
    </Button>
  }
/>
```

`ReactionBar`와 `MoveCommentsPopover`가 이 회피를 쓴다.
**툴팁이 없어져도 정보 손실은 없다** — 팝오버가 열리면서 무엇을 하는 자리인지 바로 보인다.
`aria-label`은 직접 붙여야 하므로 빠뜨리지 않는다.

### 팝오버 트리거를 `disabled`로 막을 때의 판단

**`disabled` 버튼은 클릭을 안 받으므로 팝오버가 열리지 않는다.** 팝오버 안이 유일한
설명 자리인 경우, 막는 순간 이유를 말할 곳이 함께 사라진다. 아이콘이 회색으로 죽어 있을 뿐
왜 안 되는지 알 방법이 없다.

기준은 **이유가 화면에 이미 보이는가**다.

| 막는 이유           | 방식                      | 근거                                |
| ------------------- | ------------------------- | ----------------------------------- |
| 대상이 0건          | 트리거 `disabled`         | 옮길 것이 없다는 사실이 이미 보인다 |
| 조건이 안 맞아 차단 | 팝오버는 열고 안내를 그림 | 이유가 화면 어디에도 없다           |

`MoveCommentsPopover`가 둘 다 쓴다. 댓글이 0건이면 트리거를 죽이고, 스펙 갱신 배너가
떠 있어 이동을 막을 때는 팝오버를 열어 안내 문구를 그린다(`09-comments-plan`).

**`title` 속성으로 대신하지 않는다.** `disabled` 요소에도 브라우저 기본 툴팁은 뜨지만
터치 기기에서 열리지 않는다. `ReactionBar`가 이름을 툴팁으로 빼지 않은 것과 같은 이유다 —
좁은 폭에서도 오버레이로 동작하므로 툴팁에만 있는 정보는 모바일에서 통째로 사라진다.

**`Link`로 이동하는 아이콘도 `IconButton`을 쓰지 않는다.** `<Link>`에 클래스를 직접 입힌다
(`⚙` 설정 버튼). 의미상 `<a>`가 맞고 Base UI가 `nativeButton` 경고를 낸다(`05-code-conventions`).

## `LoadingState` / `ErrorState`

조회의 대기와 실패를 표시한다. 배관 단계에서 화면마다 다르게 그리던 것을 통일했다.

```tsx
if (isPending) return <LoadingState />;
if (isError)
  return <ErrorState error={error} fallback="불러오지 못했습니다." />;
```

### 언제 쓰나

**화면이나 컬럼 전체가 대기 중일 때만 쓴다.** 둘 다 `pt-16` 중앙 정렬이라
그 영역을 통째로 차지하는 것을 전제한다.

폼 안의 한 필드만 대기 중이면 쓰지 않는다. 인라인 텍스트로 그 자리에만 표시한다 —
멤버 목록이 그 경우다. `LoadingState`를 끼우면 폼 한가운데에 위아래 64px 여백이 생긴다.

| 범위                   | 표시                                       |
| ---------------------- | ------------------------------------------ |
| 화면 전체, 컬럼 전체   | `LoadingState` `ErrorState`                |
| 폼 안의 한 필드나 목록 | 인라인 `<p className="text-sm text-fg-3">` |

### `ErrorState`의 문구

`error`를 그대로 넘긴다. `ApiError`면 서버가 보낸 한국어 문구를 그대로 쓰고,
아니면 `fallback`이 나온다. `fallback`은 **`ApiError`가 아닐 때만** 쓰이므로
서버 문구를 덮어쓰지 못한다.

**404는 서버 문구를 쓰지 않는다.** `MembershipGuard`가 거부 단계에 따라 다른 문구를 내는데
(리소스 자체가 없을 때와 남의 프로젝트일 때가 다르다) 클라이언트는 어느 쪽인지 알 수 없고,
후자의 문구는 엔드포인트 화면에서 뜬금없다. 화면이 고정 문구를 직접 쓴다.

**"찾을 수 없음"이 항상 실패는 아니다.** 스펙 상세의 중앙 컬럼은 앵커 스냅샷에 없는
엔드포인트를 `ErrorState`가 아니라 안내 문구로 그린다 — 스펙이 갱신돼 아직 안 보이는 것뿐이고
새로고침하면 나타난다. 조회가 실패한 것이 아니므로 실패 표시를 쓰지 않는다
(`06-spec-detail-plan`의 재설계 이후 절).

### 재시도 버튼

`onRetry`를 준 경우에만 그려진다. **다시 눌러 답이 달라질 때만 준다.**

| 상황                       | 재시도  |
| -------------------------- | ------- |
| 네트워크 오류, 5xx         | 준다    |
| 404 (없음, 비멤버, 삭제됨) | 안 준다 |
| 403 (권한 부족)            | 안 준다 |

전역 재시도 정책(4xx는 자동 재시도 안 함)은 `08-state-and-data`.

## 한글 입력 조합 (IME)

**`Enter`로 제출하지 않는다. 제출은 버튼만이다.**

한글은 글자가 완성되기 전까지 조합 중 상태로 있다. 이 상태에서 `Enter`는 조합을 확정하는
키인데, 브라우저가 그 `Enter`를 `keydown`으로도 흘린다. "안녕하세" 상태에서 `Enter`를 눌러
"안녕하세요"를 확정했을 뿐인데 댓글이 등록된다.

`e.nativeEvent.isComposing`으로 거르는 방법을 시도했으나 안정적으로 동작하지 않았다.
조합 확정 `keydown`이 브라우저와 IME 조합에 따라 `isComposing: false`로 오는 경우가 있어,
한 환경에서 맞춰 놓으면 다른 환경에서 어긋난다. 데모까지 남은 시간에 전 환경을 검증할 수 없어
**키 제출 자체를 뺐다.**

- `textarea`에서 `Enter`는 항상 줄바꿈이다. `preventDefault`를 걸지 않는다.
- 제출은 명시적인 버튼 클릭으로만 일어난다.
- `Shift+Enter` 규칙도 없다. 사용자에게 가르칠 조작이 하나 줄었다.
- 실시간 필터(엔드포인트 검색)는 애초에 무관하다. `onChange`로만 돌고 `Enter`를 안 본다.

**되살릴 때의 조건**: 조합 확정 `Enter`를 전 환경에서 확실히 걸러낼 수 있고, 그것을
실제 기기에서 검증했을 때만 되살린다. 코드가 도는 것과 한글이 제대로 입력되는 것은 다르다.
