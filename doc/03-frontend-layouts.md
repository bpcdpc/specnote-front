## 라우트

| 라우트              | 경로                                         | 레이아웃                               |
| ------------------- | -------------------------------------------- | -------------------------------------- |
| **Login**           | `/login`                                     | `AuthLayout`                           |
| **Signup**          | `/signup`                                    | `AuthLayout`                           |
| **Dashboard**       | `/`                                          | `AppLayout variant="dashboard"`        |
| **ProjectCreate**   | `/projects/new`                              | `AppLayout variant="project-create"`   |
| **ProjectSettings** | `/projects/:projectId/settings`              | `AppLayout variant="project-settings"` |
| **SpecOverview**    | `/projects/:projectId`                       | `SpecLayout`                           |
| **SpecDetail**      | `/projects/:projectId/endpoints/:endpointId` | `SpecLayout`                           |
| **404**             | `*`                                          | **없음** (자체 렌더)                   |

**파라미터명은 `:projectId`다.** `:id`는 어느 리소스의 id인지 알 수 없고,
엔드포인트 id가 끼면서 두 개가 되므로 전면 개명했다. 설정 화면 경로도 포함이다.

**SpecOverview와 SpecDetail은 자식 라우트 둘이지만 같은 엘리먼트를 렌더한다.**
`SpecLayout`의 `<Outlet>`이 **3컬럼 전체**를 감싸므로 셸의 소유권이 갈리지 않는다.
중앙 컬럼만 `<Outlet>`으로 만들면 좌우 컬럼과 셸이 레이아웃에, 중앙만 라우트에 걸려
소유권이 흐려진다. 그렇게 하지 않는다는 뜻이지 자식 라우트 자체를 안 쓴다는 뜻이 아니다.
페이지가 `useParams().endpointId`를 직접 읽어 있으면 상세, 없으면 `ProjectOverview`를 그린다.

> **라우터 구조 주의사항**: 파라미터를 쓰는 레이아웃은 `path`를 **부모 라우트**에 둬야 한다.
> 자식에만 두면 레이아웃의 `useParams()`가 비어 헤더 링크가 `/projects/undefined`로 나간다.

### 알림 딥링크

```
MENTIONED  /projects/:projectId/endpoints/:endpointId?comment=:commentId
INVITED    /projects/:invitedProjectId
```

초대 알림은 **프로젝트 개요까지만** 간다. 알림에 엔드포인트 정보가 없고,
초대 시점에는 사용자가 그 프로젝트에서 뭘 볼지 알 수 없다.

`?comment=`를 읽는 것은 **`CommentPanel`** 이다. 라우트나 레이아웃이 아니다 —
하이라이트는 댓글 도메인 상태이고, 그 상태를 만드는 `CommentProvider`가 거기 있다.
`CommentProvider`의 `initialHighlightedId`로 넘기고, `key={endpointId}`라
엔드포인트가 바뀌면 Provider째 새로 만들어지므로 값이 남지 않는다.

**소비하면 파라미터를 뗀다**(`setSearchParams`, `replace`). 안 떼면 세 가지가 남는다 —
주소창의 죽은 값, 같은 엔드포인트를 떠났다 돌아올 때마다 되살아나는 하이라이트,
사용자가 URL을 복사했을 때 남에게 전달되는 남의 알림 흔적.
`replace`인 이유는 뒤로가기가 같은 화면을 두 번 거치면 안 되기 때문이다.

**좁은 폭에서는 댓글 패널을 연다.** `< lg`에서 패널은 기본 닫힘인데, 슬롯 자체는
렌더되므로 하이라이트가 화면 밖에서 뜨고 스스로 꺼져 흔적이 남지 않는다.

해당 댓글이 그 엔드포인트에 없으면 **아무 일도 일어나지 않는다.** 알림 발송 후
Owner가 댓글을 옮긴 경우다. 조용한 무동작이 맞다 — "댓글을 찾을 수 없습니다"를 띄우면
사용자가 할 수 있는 것도 없이 혼란만 준다.

**404는 레이아웃 밖이다.** 존재하지 않는 경로라 프로젝트 헤더와 UserMenu가 어색하고,
`variant`도 정할 수 없다. 대신 `AuthLayout`과 같은 규칙(가로 중앙, `max-w-sm`)으로 톤을 맞추고
탈출 링크(대시보드로 돌아가기)를 반드시 둔다. 푸터는 렌더한다.

## 레이아웃 3종

### 헤더는 레이아웃이 그린다

**레이아웃이 헤더, 푸터, 골격을 소유하고, 페이지는 콘텐츠(`<Outlet>`)만 채운다.**
헤더가 필요로 하는 데이터는 페이지가 넘겨주지 않고 레이아웃이 직접 읽는다.

- 프로젝트 이름, Owner 여부 → `useQuery(["projects", id])` (`id`는 URL `useParams`에서)
- 로그인 유저 → `useAuth()`

`AppLayout`에서는 페이지와 레이아웃이 같은 queryKey를 각자 읽는다. TanStack Query가
같은 캐시를 돌려주므로 요청은 한 번이고 프롭 드릴링도 없다.
`SpecLayout`은 다르다 — 아래 절을 본다.

**알림은 레이아웃이 조립하지 않는다.** `UserMenu` 안에 있어서 두 레이아웃이 자동으로
공유한다. 헤더 슬롯에 아이콘을 하나 더 붙이지 않은 이유는, `SpecLayout`의 우측 슬롯이
`HEADER_RIGHT_WIDTH`로 폭을 계산하고 있어 요소 추가가 공짜가 아니기 때문이다.

### AppLayout의 `variant`

| variant            | 헤더 좌측 (브레드크럼)          |
| ------------------ | ------------------------------- |
| `dashboard`        | `Dashboard`                     |
| `project-create`   | `Dashboard / 새 프로젝트`       |
| `project-settings` | `Dashboard / 프로젝트명 / 설정` |

- 분기는 `projectId` 유무가 아니라 **`variant`** 로 한다.
- `←` 뒤로가기는 폐기했다. 브레드크럼이 대체한다(아래 절).
- `⚙`(설정 버튼)은 `SpecLayout` 헤더에만 있다. ProjectSettings는 이미 설정 화면이다.

**variant 분기가 늘어나는 것에 대해**: 화면이 늘면 분기가 하나씩 붙는다. 현 규모(5개 미만)에서는
감당 가능하다. variant가 7~8개를 넘거나 헤더 좌측이 복잡한 UI(검색창, 탭, 필터)를 갖게 되면
`AppHeaderLeft` 조각으로 격리하거나 페이지가 슬롯을 주입하는 방식으로 전환한다. 그 전에는 하지 않는다.

### SpecDetail을 분리하는 이유

헤더가 아니라 **본문 구조** 때문이다. Dashboard와 ProjectForm은 페이지 전체가 스크롤되지만
SpecDetail은 화면 높이에 고정되고 3컬럼이 각자 스크롤한다. 같은 레이아웃에 넣으면
높이 계산과 스크롤 소유권이 조건 분기로 얽힌다. 헤더와 푸터는 공유하므로 중복은 없다.

**`SpecLayout`은 프로젝트 조회도 갖는다.** 다른 레이아웃은 데이터를 각자 읽고 말지만
여기는 예외다. 자식 라우트 둘이 같은 페이지 컴포넌트이고 둘 다 `ProjectView`를 요구한다.
페이지에 두면 로딩과 에러 분기가 두 벌 생기고, `useSpecCache`가 `components` 없이
한 번 만들어졌다 버려진다. 레이아웃이 조회하고 `<Outlet context={{ projectView }} />`로 내린다.

**게이트 중에도 헤더는 그린다.** 프로젝트를 못 불러왔다고 화면 전체를 에러로 덮으면
대시보드로 돌아갈 길이 없어진다. 갈아끼우는 것은 `<Outlet>` 자리뿐이다.
없는 `endpointId`를 404 페이지로 보내지 않는 것과 같은 판단이다.

## 콘텐츠 컨테이너 규칙

레이아웃은 골격만 갖고, **본문의 폭과 좌우 여백은 페이지가 정한다.**

| 화면                  | 폭          | 여백         |
| --------------------- | ----------- | ------------ |
| Dashboard (목록 있음) | `max-w-5xl` | `px-8 py-6`  |
| Dashboard (빈 상태)   | `max-w-3xl` | `px-8 py-6`  |
| ProjectCreate         | `max-w-3xl` | `px-8 py-6`  |
| ProjectSettings       | `max-w-3xl` | `px-8 py-6`  |
| Login, Signup, 404    | `max-w-sm`  | `p-4` (중앙) |

- **브레이크포인트로 여백을 바꾸지 않는다.** `p-4 sm:p-6`은 639→640px에서 가로와 세로가
  동시에 점프해 콘텐츠 시작점이 튄다. 한 값으로 고정한다.
- **중앙 영역 안에서 좌상단부터 시작한다.** 빈 상태도 세로 중앙 정렬을 하지 않는다 —
  목록이 생겼을 때와 같은 지점에서 시작해야 화면 전환이 튀지 않는다.
- Dashboard만 상태에 따라 폭이 다르다(목록=카드 그리드, 빈 상태=텍스트 한 덩어리).
  전환 시 좌측 기준선이 이동하는 것은 감수한 트레이드오프다.

## 공용 조각의 책임 분리

레이아웃과 조각 사이의 경계만 여기서 정한다. 조각별 사용 규칙은 `07-components`.

| 조각          | 책임                        | 안 하는 것                |
| ------------- | --------------------------- | ------------------------- |
| `PageHeading` | 아이콘 + 제목(`h2`)         | 폭과 여백을 정하지 않음   |
| `EmptyState`  | `PageHeading` + action 버튼 | 폭을 정하지 않음          |
| `Breadcrumb`  | 조각 배열 → 경로 표시       | 조각을 스스로 만들지 않음 |
| `Header`      | 높이, sticky, 좌우 배치     | 슬롯 내용을 만들지 않음   |
| `Footer`      | 하단 고정, 정렬             | 링크를 두지 않음          |
| `Logo`        | 문자열, 폰트, 크기 기본값   | 렌더 태그를 고정하지 않음 |

**폭은 페이지가 정한다.** 공용 조각이 `max-w-*`를 들고 있으면 페이지 컨테이너와
이중으로 걸려 좌측 기준선이 어긋난다.

## 헤더

`Header`는 `left`, `right`, `wide` 세 슬롯을 받는다. `sticky top-0 z-50`이며
**스크롤 컨테이너 밖**에 두어야 한다(부모에 `overflow`가 있으면 sticky가 죽는다).
보더는 기본으로 없고 `window.scrollY > 60`일 때만 나타난다.

**슬롯을 채우는 것은 레이아웃이다.** 페이지는 `Header`를 건드리지 않는다.

| 위치    | dashboard  | project-create | project-settings | SpecLayout                          |
| ------- | ---------- | -------------- | ---------------- | ----------------------------------- |
| `left`  | 브레드크럼 | 브레드크럼     | 브레드크럼       | 목록 토글 + 브레드크럼 + `⚙`(Owner) |
| `right` | UserMenu   | UserMenu       | UserMenu         | Bearer + 댓글 토글 + UserMenu       |
| `wide`  | —          | —              | —                | Bearer(좁은 화면 2행용)             |

`SpecLayout` 좌측 순서는 **목록 토글 → 브레드크럼 → ⚙**, 우측은 **Bearer → 댓글 토글 → UserMenu**다.
패널 토글을 각 패널이 있는 쪽 끝에 붙여 어느 패널을 여닫는지가 위치로 드러나게 했다.

알림은 표에 없다. `UserMenu` 안에 있어 슬롯을 따로 차지하지 않는다.
미확인 표시는 아바타 우상단 점이다.

### 헤더 조각의 위치

`Header`는 뼈대만 갖고 내용은 슬롯으로 받는다. 그 조각들이 어느 폴더에 사는지만 정의한다.

| 조각                               | 위치                 | 이유                           |
| ---------------------------------- | -------------------- | ------------------------------ |
| 헤더 뼈대 (`Header`)               | `components/`        | 슬롯 받아 배치만 함            |
| 브레드크럼 (`Breadcrumb`)          | `components/`        | 여러 레이아웃이 공유           |
| 뒤로가기 (`BackButton`)            | `components/`        | 미사용 — 브레드크럼으로 대체됨 |
| 유저 메뉴 (`UserMenu`)             | `components/`        | 여러 레이아웃이 공유           |
| 알림 목록 (`NotificationDropdown`) | `components/`        | UserMenu 안에서 사용           |
| Bearer 입력                        | `pages/spec-detail/` | SpecDetail 전용                |
| 패널 토글 버튼                     | `layouts/SpecLayout` | 헤더 조립 주체가 직접 렌더     |
| 프로젝트 설정 버튼                 | `layouts/SpecLayout` | 헤더 조립 주체가 직접 렌더     |

### 브레드크럼

뒤로가기 버튼을 전면 교체했다. 뒤로가기는 **어디로 가는지**를 안 알려준다 —
설정 화면의 `←`가 목록으로 가는지 프로젝트로 가는지 아이콘만으로는 알 수 없다.
브레드크럼은 현재 위치와 상위 경로를 동시에 보여주고, 중간 단계로 바로 점프할 수 있다.

| 화면             | 브레드크럼                      |
| ---------------- | ------------------------------- |
| dashboard        | `Dashboard`                     |
| project-create   | `Dashboard / 새 프로젝트`       |
| project-settings | `Dashboard / 프로젝트명 / 설정` |
| SpecDetail       | `Dashboard / 프로젝트명`        |

- **마지막 조각이 `h1`이다.** 현재 위치가 곧 화면 제목이다.
- **마지막 조각도 `to`가 있으면 링크가 된다.** SpecDetail은 마지막 조각이 프로젝트 자신이라,
  엔드포인트를 열어둔 상태에서 프로젝트 개요로 돌아가는 유일한 경로가 된다.
  `to`를 줄지는 "그 조각을 눌러 갈 곳이 지금과 다른가"로 판단한다.
- SpecDetail에 엔드포인트를 붙이지 않는다. 경로가 길고 사이드바에 이미 선택 표시가 있다.
- 프로젝트명은 `truncate`. 긴 이름이 헤더를 밀어내지 않게 한다.
- **프로젝트를 아직 못 받았거나 실패했으면 그 조각을 아예 뺀다.** `Dashboard`만 남는다.
  "프로젝트" 같은 대체 텍스트를 넣지 않는다 — 그 자리가 `h1`이라, 없는 이름을 잠깐
  제목으로 읽히게 하는 셈이다. 조각이 하나 늘었다 줄어드는 쪽이 낫다.

### 반응형

브레이크포인트는 **`md`(개념)** 와 **`lg`(실제 분기)** 둘이다.
값이 갈리는 지점은 전부 **`lg`(1024px)** 이다.

```
넓은 화면 (≥ lg)
┌────────────────────────────────────────────────────────┐
│ ☰ Dashboard / 결제 API ⚙   [Bearer 토큰__] 💬 아바타   │   1행
└────────────────────────────────────────────────────────┘

좁은 화면 (< lg)
┌────────────────────────────┐
│ ☰ Dashboard / 결제 API ⚙  💬 아바타 │   1행
│ [Bearer 토큰____________________]   │   2행
└────────────────────────────┘
```

- Bearer는 **자리를 옮길 뿐 사라지지 않는다.**
- 구현은 `order` + `flex-wrap`. **DOM을 두 벌 렌더하지 않는다.**
- **2행 전환 기준도 `lg`다.** `SpecPanelsContext.isWide`를 3컬럼과 공유한다.
  768~1024 구간은 3컬럼이 이미 오버레이라 헤더에도 여유가 없다. 같은 값이 맞다.
- 그 외 화면 헤더는 요소가 적어 모든 폭에서 1행 유지.

## 푸터

하단 고정, `pointer-events-none`. 아래 요소의 클릭을 막지 않으므로
**링크를 두지 않는다**(클릭이 통과한다). 본문은 32px만큼 `pb`를 확보한다.

**배경은 텍스트 폭만큼만 깐다.** 완전히 투명하면 스크롤된 본문 글자와 겹쳐 둘 다 안 읽히고,
가로로 꽉 찬 띠를 깔면 `h-dvh` 화면에서 없는 경계선이 생긴다.
`align` prop은 `"left" | "center" | "right"`.

푸터 로고는 장식이므로 `<Logo as="span">`으로 렌더한다(heading 계층은 `07-components`).

## 스크롤 구조

| 레이아웃     | 스크롤 주체                                    |
| ------------ | ---------------------------------------------- |
| `AuthLayout` | 없음 (화면에 들어감)                           |
| `AppLayout`  | **문서 전체** (`min-h-dvh`, window 스크롤)     |
| `SpecLayout` | **각 컬럼** (`h-dvh` 고정, 페이지 스크롤 없음) |

`h-dvh`를 쓰는 이유: `100vh`는 모바일에서 주소창을 포함한 높이라 화면 아래가 잘린다.

스크롤 컨테이너에는 **`overscroll-none`** 을 준다. 없으면 컬럼 끝에 닿았을 때
스크롤이 부모로 넘어가 페이지 전체가 흔들리고, 모바일에서는 당겨서 새로고침이 걸린다.

**스크롤 컨테이너를 겹치지 않는다.** 팝업 안에 목록을 넣을 때는 바깥의 `overflow`를 끄고
안쪽 하나만 스크롤시킨다. 둘 다 켜면 안쪽 끝에 닿는 순간 바깥이 이어서 밀린다.
`UserMenu`의 알림 목록이 이 경우다 — 팝업의 `overflow-y-auto`를 끄고 목록에만 `max-h`를 준다.

## SpecDetail 3컬럼

**양쪽 다 리사이즈되고 양쪽 다 접힌다.** v0.4의 "왼쪽 고정폭"은 폐기했다.

| 컬럼   | 기본    | min | max | 리사이즈 | 접기 | 스크롤 |
| ------ | ------- | --- | --- | -------- | ---- | ------ |
| 왼쪽   | 330px   | 240 | 400 | ✅       | ✅   | 세로   |
| 중앙   | 남는 폭 | 320 | —   | —        | —    | 세로   |
| 오른쪽 | 440px   | 240 | 600 | ✅       | ✅   | 세로   |

- 값의 출처는 `panelMetrics.ts`의 `COLUMN`이다. 이 표는 그 사본이므로
  **코드를 고치면 여기도 같이 고친다.**
- 구현은 `react-resizable-panels` **v4**. 보더는 두지 않고 호버 시 드러나는
  구분선(`Separator`)이 경계 역할을 한다(`04-design-tokens`).
- 오른쪽이 왼쪽보다 넓고 max도 600인 이유는 댓글이 긴 텍스트이기 때문이다.
  헤더 우측 슬롯 폭(`HEADER_RIGHT_WIDTH`)이 이 값에서 좌우 패딩을 뺀 값이라,
  오른쪽 기본폭을 바꾸면 헤더의 Bearer 입력 폭도 같이 움직인다.
- 접기 토글은 헤더에 있다. 좌측은 목록 토글, 우측은 댓글 토글.
- **중앙 컬럼은 5상태다.** 미선택(프로젝트 개요) / 잘못된 `endpointId`(요청을 보내지 않음) /
  로딩 / 실패 / 상세. 어느 상태든 **양쪽 컬럼은 그대로 산다.** 링크가 상해도
  다른 엔드포인트로 갈 경로를 남긴다.
- 스펙 갱신 배너는 3컬럼 위, 헤더 아래에 붙는다. `shrink-0`이라 컬럼 높이만 줄인다.

### `lg`(1024px) 분기

| 폭     | 동작                                                         |
| ------ | ------------------------------------------------------------ |
| `≥ lg` | **밀어내기** — 3컬럼이 나란히. 접으면 중앙이 그만큼 넓어진다 |
| `< lg` | **덮기** — 양쪽이 오버레이(`w-full max-w-2xl`). 기본 닫힘    |

덮기 모드에서는 **하나만 열린다.** 백드롭 클릭과 `Esc`로 닫는다.
둘이 동시에 열리면 좁은 화면에서 중앙이 완전히 가려진다.

**덮기 모드에서도 슬롯은 렌더된다.** `translate-x-full`로 화면 밖에 밀어놓을 뿐
DOM에는 있다. 그래서 닫힌 채로도 댓글 쿼리가 돌고, 알림 딥링크가 도착했을 때
패널을 열어주지 않으면 하이라이트가 화면 밖에서 소진된다(위 알림 딥링크 절).

**1024를 고른 근거는 최소폭이다.** `240 + 320 + 240 + 구분선 2 = 802px`.
`md`(768)로 가르면 768 < 802라 세 컬럼이 최소폭조차 못 채워 레이아웃이 깨진다.
802보다 위에 있으면서 표준 브레이크포인트인 값이 `lg`다.

기본폭이 아니라 최소폭을 기준으로 잡는다. 기본폭은 사용자가 드래그하면 어차피 바뀌는
출발값이고, 레이아웃이 성립하느냐를 정하는 것은 최소폭이다. 기본폭을 기준으로 삼으면
컬럼 폭을 조정할 때마다 브레이크포인트를 다시 계산해야 한다.

**`min-w-[900px]` 가로 스크롤은 폐기했다.** 좁은 화면에서 가로로 밀어 보게 하면
세로 스크롤과 가로 스크롤이 겹쳐 조작이 어긋난다. 덮기 모드가 대신한다.
차단 화면("데스크탑에서 이용해 주세요")도 만들지 않는다.

> **와이어프레임 v0.1과의 차이**: 와이어프레임은 양쪽 리사이즈로 그려져 있는데
> **구현이 그쪽으로 돌아왔다.** v0.4에서 "왼쪽 고정"으로 적었던 것이 어긋난 기술이었다.
> 남은 차이는 접기와 `lg` 오버레이로, 와이어프레임에는 둘 다 없다.
